# 120F

an iOS tweak that's capable of arbitrarily modifying graphical related settings in Limbus Company by leveraging public classes found in Assembly CSharp.

the sole purpose of this tweak is to give more flexibility and fine-tuning capabilities regarding graphical settings targeting performance.

## What's included

- Independent Normal/Combat FPS targeting by calling `UnityEngine.Application.set_targetFrameRate` directly through IL2CPP - not by spoofing a `CADisplayLink`. A display link is just UnityFramework's own frame pacer, downstream of Unity's real `targetFrameRate`; Unity resyncs it on virtually every scene/config reload (most visibly loading screens), which would silently revert a spoofed value. Writing `targetFrameRate` itself removes that footgun. There's no timer re-asserting the value against something fighting it, either - a scene-state poll (`FPS120Controller`, originally written just to flip Menu/Combat FPS on entering/leaving a battle node) now also detects the transition back to a non-battle scene and re-pushes every setting in the panel, not just FPS, since a loading screen resets far more than the frame rate.
- A pull-tab debug panel (`GraphicsDebugOverlay.m`) for live-tuning render settings: texture mip limit, render scale, MSAA, HDR, extended URP Post FX (Motion Blur, Chromatic Aberration, Vignette, Film Grain, Lens Distortion, White Balance, Saturation, Tonemapping), and Camera AA (antialiasing mode/quality/dithering).
- A Mods section (same panel) for swapping in desktop-coded FMOD `.bank` mods on mobile - see `BankTransplant.h`/`.m`. The mobile client plays Vorbis-coded FSB5 samples natively, so this is a direct file swap - no re-encoding.

None of this touches `LocalGameOptionData` or the save system - values are live/in-memory only, and opening the game's own settings menu and hitting Apply will stomp them back to the last saved preset. See the header comment in `GraphicsDebugOverlay.m` for the full list of caveats (e.g. Bloom controls were confirmed dead in-game and removed; Camera AA is unvalidated against the live binary since a UI-heavy gacha/VN game may route battle/story through untagged cameras).

## Layout

- `GDScripts.h` / `.m` - every IL2CPP-mediated engine call in the tweak: frame rate and the scene-state poll (`FPS120Controller`), QualitySettings/urpAsset (texture mip, render scale, MSAA, HDR), the URP Volume Post FX stack, renderer features, and camera AA/dithering. Also owns the hardcoded setting defaults, the current-value globals every row in the panel reads/writes, and JSON settings persistence. This is the only file that reaches into the game's managed classes.
- `GraphicsDebugOverlay.m` - UI only. Builds the panel and calls into `GDScripts.h` to read/write each control's current value and push a change to the engine.
- `IL2CppBridge.h` / `.m` - low-level, feature-agnostic wrapper around the handful of `libil2cpp` C API entry points (class/method/field lookup, invoke). `GDScripts.m` is its only caller.
- `fps120.m` - dylib entry point/startup glue only: waits for the runtime to be ready, then hands off to `FPS120Controller` and configures the Unity view's Metal layer.
- `BankTransplant.h` / `.m` - imports a modded FMOD `.bank` by directly replacing the matching stock `.bank` under `Documents/Assets/Sound/FMODBuilds/Mobile` with the modded file's bytes as-is - no decoding, re-encoding, or header rebuilding, since the mobile client already plays Vorbis-coded FSB5 samples natively. The original stock bank is backed up once before modification. `GraphicsDebugOverlay.m`'s Mods section (Import Bank Mod / Restore Originals) is the only caller.

- `PatchManifestNetwork.h` / `.m` - hooks the game's own `NSURLSession` delegate to intercept its FMOD manifest fetch (`FmodPatchInfo.json`) in flight and zero out every entry's Hash/Size in the response's `Files` dictionary before it reaches the game, so locally-swapped assets don't fail its integrity check. Deactivates itself for the rest of the session once it's patched a manifest once. `BankTransplant.m`'s and `BundleTransplant.m`'s swaps don't call into this directly - it works passively at the network layer whenever the game itself fetches the manifest.
- `SerializedObjectTable.h` / `.m` - one layer inside a UnityFS archive's own `CAB-...` node: reads/patches an individual `SerializedFile`'s object table (every asset inside a bundle - PathID + byte range), version 22 only. Also structurally locates `m_TargetPlatform` in the SerializedFile header for in-place rewriting. Foundation for the Texture2D retarget pipeline below.
- `TextureAtlasTransplant.h` / `.m` - now backup/restore only (`+restoreAllBackedUpBundlesWithError:` / `+restoreBackedUpBundlesForCAB:error:`), so atlas backups an earlier build wrote can still be reverted. Its object-level diff/transplant pipeline (matching a modded bundle's PathIDs against a cached target and swapping whichever differed) was already dead code before this cleanup - see the Texture2D retarget pipeline note below - and has been removed along with it.
- `Texture2DPixelDecoder.h` / `.m`, `CrunchTextureDecoder.h` / `.mm` - DXT1/DXT5 block decoders and a vendored Crunch (DXT5Crunched) transcoder, both decoding to plain RGBA32. Format-agnostic building blocks, wired into the Texture2D retarget pipeline's Layer C (`Texture2DConverter.h`/`.m`) - see the Texture2D retarget pipeline section below.

`GameEngineControl.h`/`.m` doesn't exist - earlier versions of this README described it as the intended home for the engine calls above, but it was never actually built. `GDScripts.h`/`.m` is that file, under a different name.

## Texture2D retarget pipeline

The whole-bundle Texture2D retarget pipeline (rewrite a desktop bundle's `m_TargetPlatform` from Windows Standalone x64 (19) to iOS (9), re-encode desktop-compressed `Texture2D` pixel payloads to RGBA32) was torn out and rebuilt from scratch. The previous implementation (`Texture2DFields.h`'s version-profile guessing, `RawPixelPacker.h`, `PlatformBundleRetarget.h`/`.m`) parsed Limbus Company's Unity 6000.3.12f1 `Texture2D` layout using a schema that doesn't match the real one - two fields it assumed present (`m_VTOnly`, `m_AlphaIsTransparency`) aren't serialized in this build at all, which is the direct cause of the `+4`-byte cursor drift that kept surfacing as `m_TextureFormat` parse failures.

See `Rework.txt` (project root) for the full root-cause writeup and the replacement architecture: a fixed, single-schema structural parser for this exact Unity build (no profile detection), a disk-backed writer that never holds a whole converted bundle in memory, and RGBA32-only output (no further re-pack). Picking a bundle-kind mod file in the Mods panel now runs this pipeline end to end (see `GraphicsDebugOverlay.m`, below). Bank-kind mods (`BankTransplant.h`/`.m`, a direct FMOD `.bank` byte swap with no Unity object parsing involved) are a completely separate mechanism, unaffected by any of this.

All four layers of Rework.txt's architecture, plus its validation pass and the overlay entry point, are done:

- `Texture2DSchema.h`/`.m` (Layer B) - the fixed structural Texture2D parser Rework.txt calls for: one schema, for exactly Limbus Company's Unity 6000.3.12f1 build, no candidate profiles and no fuzzy search for `m_TextureFormat`. Validates dimensions/mip count/format against the corpus Rework.txt surveyed and requires `m_StreamData` to consume the object's bytes exactly - a structural parser that's self-verifying rather than self-correcting, per Rework.txt's own closing argument. Read-only: `NSData` in, a `ZSTexture2DInfo` (dimensions, format, every byte offset a later patch step needs) out.
- `BundleTexture2DEnumerator.h`/`.m` (Layer A + B glue) - given a bundle path, decompresses it (`UnityBundleCAB`), parses its primary node's object table (`SerializedObjectTable`), and schema-parses every Texture2D (class ID 28) object found. Failures are reported per-object, not fatal to the whole bundle. Also resolves (not decodes) each texture's still-encoded source pixel bytes, whether inline or in a companion `.resS` node - the exact input Layer C (`Texture2DPixelDecoder.h`/`CrunchTextureDecoder.h`, both already implemented) needs for the next step.
- `Texture2DConverter.h`/`.m` (Layer C wiring) - the conversion decision table (`+conversionDecisionForRawFormat:` - RGBA32/ASTC 4x4/ASTC 6x6 left unchanged, RGB24/DXT1/DXT5/DXT5Crunched decoded to RGBA32, anything else fails closed) plus the driver (`+convertObjectsInEnumerator:handler:`) that calls each successfully schema-parsed Texture2D object through `Texture2DPixelDecoder` (which already routes DXT5Crunched through `CrunchTextureDecoder` internally) one object at a time, inside its own `@autoreleasepool`, handing each result to a caller-supplied block rather than accumulating an array - see the header's MEMORY POSTURE note. This produces RGBA32 bytes in memory only; nothing is written to disk or patched into an object yet.
- `BundleTexture2DRetargeter.h`/`.m` (Layer D) - `+retargetBundleAtPath:toPath:error:` actually produces a retargeted bundle: patches `m_TargetPlatform` (19 → 9) in place via `SerializedObjectTable`'s already-located offset, and for every Texture2D `Texture2DConverter` says needs converting, stages its RGBA32 bytes into a brand-new disk-backed `.resS`-shaped node (never growing/touching any pre-existing one), rewrites that object's format/size/mip-count/`m_StreamData` fields, and appends the small rewritten object at the true end of the CAB node's own data - the same append-and-patch-one-table-entry pattern `SerializedObjectTable insertObjects:...` already uses - rather than reflowing every object after it. Writes the result via `UnityBundleCAB`'s existing (previously unwired) streaming writer. Per-object failures are reported, not fatal to the whole bundle - see the header for what's guaranteed vs. what's refused outright (e.g. a converted object whose rewritten bytes would exceed its original span).
- `BundleTexture2DRetargetValidator.h`/`.m` (Rework.txt's "Validation strategy") - run AFTER `BundleTexture2DRetargeter` has already written a destination bundle: re-enumerates both the original bundle and the freshly-written one from scratch (through the same `BundleTexture2DEnumerator`/`Texture2DSchema`/`SerializedObjectTable` code every earlier layer already uses, not new parsing logic) and cross-checks the rebuilt one - `m_TargetPlatform` reads back as 9, object count unchanged, every original PathID still resolves, every converted object reparses with format 4/mip count 1/expected `m_CompleteImageSize`/a resolvable `StreamingInfo` pointing inside the new resS node, every other object's declared pixel byte range still resolves. Reports per-object (`ZSTexture2DRetargetValidationReport.issues`) rather than failing outright on the first discrepancy - only returns nil if either bundle can't be re-enumerated at all.
- `GraphicsDebugOverlay.m`'s `-gd_retargetValidateAndSwapBundleAtURL:swappedCount:` (the bundle-kind branch of `-gd_handlePickedModURLs:intoFolder:`, the Mods panel's picker-completion handler) - the entry point that ties the above together for a picked bundle-kind mod file: `BundleTexture2DRetargeter` writes a retargeted copy to a scratch path, `BundleTexture2DRetargetValidator` re-reads and cross-checks it, and only `report.passed == YES` reaches `+[BundleTransplant transplantAndSwapModdedBundlesAtURLs:error:]` - this project's existing swap-in-place machinery (CAB-matched backup + atomic replace of every matching cached `__data`, same mechanism the panel's "Restore Bundles & Banks" button already knows how to undo). A failure at any stage is reported back per-file (same "report per item" posture every layer below it already uses) and nothing is swapped into the game's cache. The scratch retargeted bundle never persists past one call - the picked file's own (desktop-target) bytes are what gets tracked in the Mods Library accordion, same as every other mod kind.
